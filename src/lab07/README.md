# Лабораторная работа №7 — поиск, сортировки и измерение времени

## Реализация

В search.py реализованы линейный и бинарный поиск, Two Sum перебором пар и со словарём. Линейный поиск возвращает первое вхождение, бинарный — любое. Отсутствие элемента обозначается -1; отсутствие пары — None. Индексы в паре различны и идут по возрастанию.

В sorting.py реализованы сортировки пузырьком, вставками и выбором. Они возвращают новый список и не меняют исходный. Готовые сортировки, min и max внутри алгоритмов не используются. В пузырьке есть ранний выход, если за проход не было обменов.

## Запуск

Из корня проекта:

```powershell
python -m src.lab07.check
python -m src.lab07.bench
```

check.py сравнивает сортировки с sorted, поиск с list.index, а Two Sum проверяет по наличию решения и правильности суммы. Разные правильные пары допустимы. Используется seed 42, 100 случайных прогонов каждого типа плюс явные крайние случаи: пустые списки, один элемент, повторы, обратный порядок. Результат: **OK: 523 проверок наборов данных**. Для поиска каждый набор проверяется несколькими запросами. Расхождений не найдено.

## Бенчмарк

Замеры выполняются timeit, по одному запуску. Каждая сортировка получает одинаковые данные. Генерация не входит во время, seed равен 42. Для поиска используются 10 000 одинаковых запросов к 100 000 элементам; стоимость предварительной сортировки приведена отдельно. Для Two Sum единственная подходящая пара помещена в конец, чтобы измерить полный перебор.

На 100 000 элементах квадратичные сортировки запускаются в отдельном процессе с лимитом 60 секунд. Метка >60 означает фактическое превышение лимита, а не оценку. Время запуска процесса не входит в возвращаемый замер, но входит в лимит ожидания. Запись CSV выполняется через write_csv из ЛР4.

## Выводы

Пузырьковая сортировка на случайных данных выполняет порядка n² сравнений, поэтому при увеличении n в 10 раз ожидается замедление примерно в 100 раз. Встроенный sorted имеет сложность O(n log n), поэтому теоретический рост на таких размерах — около 12–13 раз, а не 100. Реальные отношения отличаются из-за случайных данных, малого времени быстрых операций и нагрузки компьютера. Проверка на случайных данных и крайних случаях прошла без расхождений; исходные списки не изменяются.

Бинарный поиск отбрасывает половину диапазона на основании порядка элементов, поэтому без предварительной сортировки он может пропустить существующее значение. Для одного запроса линейный поиск обычно выгоднее сортировки с последующим бинарным поиском. При большом числе запросов стоимость O(n log n) подготовки окупается: каждый следующий запрос требует O(log n) вместо O(n). Замеры поиска в таблице относятся ко всему пакету из 10 000 запросов; время подготовки указано отдельно.
